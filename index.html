Sec. 1What this is

I wrote print.py as a sequence of small, independent demonstrations, and I keep the order fixed because the order is the lesson. Each block shows one behaviour on its own. The script contains no input, no functions, and no output file. It only prints.

I set this page as a press proof sheet because that is the closest match for the file itself. Each strategy gets struck as its own proof: the code that set it, the exact line it printed under a red rule, and my note on what the proof shows. The last proof prints nothing at all, on purpose, because the end of the file is about comments.

Run the whole sheet at once from the repo root:

python3 print.py

Sec. 2The proofs, in file order

Proofs strike in one by one as you read down the sheet, the way impressions come off a press. Each one settles once and then stays still. The output under each code block is the output of that block on its own, word for word, including where a line ends and where it does not.

1OK

Print a variable

print.py lines 10 to 11

data = "Fun secret variable"
print(data)
Struck line
Fun secret variable

I start with a variable on purpose. Printing the variable prints the value it holds, not the name I gave it, and that difference is the first thing a new reader trips on.

2OK

Print a string

print.py line 12

print("Hello World")
Struck line
Hello World

No variable, no setup. The string goes in, the string comes out, and print adds the newline at the end on its own.

3OK

Print numbers

print.py lines 13 to 15

print(50)
print(1000)
print(3.142)
Struck lines
50
1000
3.142

Two integers and a float, each on its own line because each call ends its own line. No quotes are needed around the numbers, and none are printed.

4OK

Print several values in one call

print.py line 19

print(50, 1000, 3.142, "Hello World") # Comma separation
Struck line
50 1000 3.142 Hello World

I pass these four values in one call and let the commas do the work: print puts exactly one space between values on its own, so I do not need to add spaces inside the strings myself. The words after the code on that line are an end of line comment. The interpreter ignores them.

5OK

Stay on the same line, end=""

print.py lines 26 to 27

print("Hello", end="")
print("World")
Struck line, no space in it
HelloWorld

I use end="" here to replace the newline entirely, so the next print continues right where this one stopped and the two words run together. This proof only makes sense against the default it overrides: print ends the line unless I tell it not to.

6OK

Stay on the same line, end=" "

print.py lines 29 to 30

print("Hello", end=" ")
print("World")
Struck line, one space in it
Hello World

Same move, one character different. With end=" " I leave exactly one space instead of nothing, which is the only difference between this proof and the one before it. Put side by side, the pair shows what end actually controls.

7OK

End of line comments

print.py lines 32 to 33

print(50)  # This line prints 50
print("Hello World")  # This line prints Hello World
Struck lines
50
Hello World

Each comment sits after the code it explains, on the same line. The printed output is the same as if the comments were not there. They are for the reader, not for the run.

8OK

Comments that print nothing

print.py lines 40 to 44, and lines 51 to 53

# This is just a comment hanging out on its own!

# For multi-line comments, we must
# add the hashtag symbol
# each time
"""Docstrings are pretty cool
for writing longer comments
or notes about the code"""
Struck line
(nothing printed)

The rest of the file is about comments themselves, so here the comments are the content I am demonstrating, not notes about the printing above. Everything on a line after the hashtag is ignored when the file runs. The last block needs care from me: it looks like a comment, but it is really a string. It only reads as documentation because it sits here as a bare expression that nothing uses.
